# Alltynex 한글 패치 빌드

이 프로젝트는 FM TOWNS용 Alltynex의 본문을 한글로 출력하는 패치 ISO를 만든다. 번역은 CSV에서 편집하고, 한글 모양은 외부 폰트의 자모를 조합해 만든다. 생성한 ISO는 FreeTOWNSOS로 부팅한 뒤 게임을 자동 실행한다.

이 문서는 빌드를 실행하거나 번역을 편집하는 사용자를 위한 안내다. 원본 게임의 함수·주소·자료 형식은 [소스 분석](Alltynex-Source-Analysis.md)에 있다.

- 한글이 출력되는 원리: [4. FNT·조합 토큰·음절 합성](#4-fnt조합-토큰음절-합성)

## 1. 시작하기

### 준비

원본 Alltynex는 개발자가 [SITER SKAIN의 배포 페이지](https://www.siterskain.com/artifact/)에서 무료로 제공한다. **ALLTYNEX for FM TOWNS** 링크로 받은 뒤 `Import/Img`에 둔다.

현재 빌드는 Python 3.14로 빌드했다. 프로젝트 루트에서 작업한다.

| 위치 | 준비할 자료 |
| --- | --- |
| Import/Img | 원본 게임 자료와 FreeTOWNSOS 부팅 입력 |
| Import/Strings | 번역 CSV와 한글 조합 토큰표 |
| font | HANME 자모 폰트 |
| licenses | 폰트·프로젝트·외부 자료 라이선스 |
| Output | 빌드가 생성하는 ISO와 xdelta |

입력 자료의 일치 여부는 빌더가 검사한다. 필요한 자료가 없거나 지원하는 자료와 다르면 로그에 표시된 입력 오류를 먼저 해결한다.

### 명령줄로 빌드

프로젝트 루트에서 실행한다.

```powershell
python tools/build_alltynex_korean_freeos_from_zip.py
```

완료되면 Output에 `Alltynex (Kor v1.0).iso`와 `Alltynex (Kor v1.0).xdelta`가 생성된다. xdelta는 압축을 풀지 않은 원본 `alltynex_fmtowns.zip`을 기준으로 완성 ISO를 복원한다. 빌드 로그에 실패가 표시되면 새 결과물이 완성된 것으로 취급하지 않고 원인을 확인한다.

Windows x64에서는 `tools/xdelta3.exe`에 포함된 [공식 xdelta3](https://github.com/jmacd/xdelta) v3.2.1을 사용한다. 빌드 중 다운로드는 하지 않는다. 다른 환경에서는 xdelta3를 PATH에 설치하거나 빌드 명령에 `--xdelta3 PATH`를 추가한다.

### 배포된 xdelta 적용

원본 ZIP과 xdelta, xdelta3만 준비하면 된다. Windows x64에서는 포함된 `tools/xdelta3.exe`를 원본 ZIP·xdelta와 같은 폴더에 복사하고, 그 폴더에서 다음 명령으로 ISO를 만든다. ZIP은 압축 해제하지 않는다.

```powershell
.\xdelta3.exe -d -D -R -s alltynex_fmtowns.zip "Alltynex (Kor v1.0).xdelta" "Alltynex (Kor v1.0).iso"
```

PATH에 설치된 xdelta3를 사용할 때는 명령의 `.\xdelta3.exe`를 `xdelta3`로 바꾼다.

기준 ZIP의 SHA-256은 `19b662f038e50e99535f60dbe6e07a77e269f574ed9250d46fc0655bb2aa6b3a`다. 적용 사용자에게는 Python·CSV·폰트·FreeTOWNSOS 입력 ISO가 필요하지 않다. 직접 번역을 편집해 빌드할 때는 위 준비 자료가 모두 필요하다.

### 빌드 결과와 실패 복구

ISO와 xdelta는 임시 경로에서 모두 생성한 뒤 결과 파일을 교체한다. 생성 실패 시 기존 결과를 보존하고, 교체 실패 시 이미 교체한 파일을 복구한다. 복구도 실패하면 `Output/alltynex-build-*`에 기존 결과 백업과 `RECOVERY.txt`를 보존하며 로그에 위치를 표시한다.

빌드·토큰표 갱신은 같은 작업 공간의 운영체제 잠금을 공유한다. 다른 작업이 진행 중이면 새 쓰기 작업을 중단한다. 정상 종료와 프로세스 종료 시 잠금은 해제된다.

다른 번역 CSV를 사용하려면 빌드 명령에 `--translation-csv PATH`를 추가한다.

### 게임 실행

에뮬레이터의 CD 이미지로 생성 ISO를 지정하고 새로 부팅한다. ISO의 자동 실행 배치가 게임을 시작한다.

### 편집 후 자주 만나는 오류

| 상황 | 확인할 점 |
| --- | --- |
| EGB 문장이 너무 길어 빌드 실패 | 한글 토큰은 2바이트다. 79바이트 본문 한도와 화면 너비를 확인하고 기존 행 사이에서 번역을 재배치한다. |
| 화면 오른쪽을 넘어감 | X좌표, 24px 문자 폭, 12px 공백 폭을 함께 계산한다. |
| 새 한글 음절을 입력함 | 빌드 때 토큰이 자동 추가된다. 전체 토큰 수의 현재 한도는 376개다. |
| SPR UI에 한글을 넣어 오류 | 현재 일반 SPR UI는 기존 영문·숫자 글리프를 사용한다. |
| 같은 타이틀 주소의 번역이 충돌 | ASCII_UI와 SPR_TITLE 별칭의 서로 다른 수정값을 정리한다. |

## 2. 적용 범위와 산출물


게임 실행 이미지에 외부 자모 폰트 적재와 한글 조합 출력 함수를 추가한다. EGB는 본문을 그리는 BIOS 기능이고, SPR은 미리 등록된 글자 그림을 배치하는 스프라이트 기능이다.

| 경로 | 적용 범위 | 출력 방식 |
| --- | --- | --- |
| EGB 오프닝 | 29행 | HANME 자모 조합 + 기존 EGB 비한글 출력 |
| EGB 스탭롤 | 원본 80슬롯 중 CSV의 39행 | 같은 공용 EGB 후크 |
| EGB 엔딩 | 6행 | 같은 공용 EGB 후크 |
| SPR UI | 77개 고유 주소, 0x3BFEC~0x3F32E | 기존 영문·숫자 SPR 글리프 |
| 타이틀·스코어 하단 | 0x3E2DC, 0x3E89C | 1996 SATOSHI YOSHIDA KR1.0 |

EGB는 총 74행이다. 일반 SPR UI의 한글 조합 렌더러는 배포 빌드에 포함하지 않는다. 외부 FNT를 SPR 한 글자로 출력하는 기능은 개발 단계에서 확인했다. 그 시험 구현은 현재 배포 빌드에 포함되어 있지 않다. EXP 외 일본 원본 게임 파일 95개는 그대로 보존한다.

### 생성물과 자동 실행


| 생성물 | 기록 시점 크기·지문 |
| --- | --- |
| Output/Alltynex (Kor v1.0).iso | 5,222,400바이트 |
| Output/Alltynex (Kor v1.0).xdelta | 795,824바이트 |
| ISO의 ALLTYNEX.EXP | 924,640바이트 |
| ISO 안의 HANME.FNT | 25,936바이트 |

ISO의 `/ALLTYNEX`에는 ZIP 원본 96개 중 EXP를 패치본으로 바꾸고 HANME.FNT를 추가한 97개 파일을 둔다. ZIP에 없던 설치 컨테이너 ALLTYNEX.EXE·저장 설정 CFGDAT.SAV는 가져오지 않는다. OS 파일과 TESTS를 보존하며 자동 실행은 `AUTOEXEC.BAT → KRSTART.BAT → FORCE31K.COM → CD \ALLTYNEX → RUN386.EXE -nocrt ALLTYNEX`다.

## 3. 번역 CSV와 편집 규칙

번역 입력은 [Alltynex_Korean.csv](../Import/Strings/Alltynex_Korean.csv)다. CSV의 번역·메모·EGB X좌표를 편집한 뒤 다시 빌드한다. 현재 열의 의미는 다음과 같다.

| 열 | 의미 |
| --- | --- |
| type | EGB 본문·SPR UI 등 문자열 종류 |
| exp_offset | 원본 압축 실행 이미지에서 대상 레코드가 시작하는 주소 |
| x, y | EGB 문자열의 시작 X좌표와 글자 아래쪽 Y좌표. X는 편집할 수 있으며 Y는 원본 값을 유지한다. |
| japanese_original | 일본 원문; 대조 기준 |
| korean_patch | 실제 출력할 번역·UI 문구와 배치 공백 |
| notes | 작업 메모 |

영문 패치 문구의 대조 자료는 [소스 분석](Alltynex-Source-Analysis.md)에 있다.

EGB의 X는 CSV 값을 화면 시작점으로 직접 사용한다. 오프닝 기본 X는 32px다. SPR 문자열에는 이 방식의 X 필드를 적용하지 않는다. CSV를 편집할 때 헤더·열/행 순서와 UTF-8 인코딩을 유지한다.

EGB 본문은 CP932 비한글 + 2바이트 한글 토큰으로 인코딩한다. 본문 용량은 79바이트이며 원본 물리 레코드의 문자열 저장 영역은 80바이트다. 기존 BIOS len=40을 그대로 전체 번역 길이로 사용하는 방식이 아니라, 출력할 세그먼트 레코드를 생성한다. 자동 줄바꿈은 없으므로 문장을 나눌 때는 기존 CSV 행 사이에서 번역을 재배치한다. 행 수와 주소는 유지한다. 빈 번역은 길이 0의 출력으로 반영하며 원문으로 되돌리지 않는다.

빌더는 비한글 인코딩을 검사한다. EGB의 C0·DEL·C1 제어문자와 F0/F1 한글 토큰에 충돌하는 CP932 사용자 정의 문자를 거부한다. SPR UI는 출력 가능한 ASCII만 허용한다. 빌더는 최종 79바이트 한도를 강제한다.

### 좌표와 가운데 배치

공백·전각 공백은 12px, 그 외 표시 단위는 24px 이동한다. 원본 일본어의 선행 전각 공백도 CSV에 보존한다. 스탭롤·엔딩 45행은 X=80px를 기준으로 번역 앞의 전각 공백으로 가운데 배치한다. Y·행 순서·스크롤 간격은 유지한다.

앞뒤 배치 공백을 뺀 본문 이동폭을 W라 하면 선행 공백 수는 `(480-W+12)//24`다. 화면 중앙 320px와 최대 6px 차이의 가장 가까운 12px 단위 배치다. 빈 행에는 공백을 넣지 않는다. 이 배치는 CSV에 저장한 값이며 빌드가 번역을 재작성하거나 자동 가운데 정렬하지 않는다. 본문·내부 공백을 바꾸면 선행 공백을 다시 맞춰야 한다.

## 4. FNT·조합 토큰·음절 합성

### 자모 파일

원형 han_hanme.fnt는 16×16 1bpp 자모 360개다. 각 자모를 24×24로 변환하며 원형 픽셀 선택은 `source = destination * 2 // 3`이다. 원형 변환의 24×24 출력은 100% 화면 배율에서 확인됐다. 현재 빌드는 이 변환을 사용한다.

| 오프셋 | 크기 | 값 |
| --- | ---: | --- |
| 0x00 | 8 | HMEFNT01 |
| 0x08 | 2 | 자모 수 360, little endian |
| 0x0A | 1 | 폭 24 |
| 0x0B | 1 | 높이 24 |
| 0x0C | 4 | 자모당 72바이트, little endian |
| 0x10 | 25,920 | 자모 비트맵 |

생성 FNT MD5는 `324968380BF92353565FDAFF3AB38920`이다. 폰트는 메모리에서 생성하여 ISO에 포함한다. 총 25,936바이트다. 비트맵은 MSB-first, 행당 3바이트다. 디스크 파일 길이와 별개로 적재 버퍼 뒤에 0 보호 영역을 둔다.

### 토큰표 생성

완성형 음절 코드에서 `n = ord(음절)-0xAC00`, `초성, 나머지 = divmod(n,588)`, `중성, 종성 = divmod(나머지,28)`로 분해한다. 종성 0은 받침 없음이다. 모음·받침 유무·초성 종류에 따라 HANME 문맥별 자모 슬롯을 선택한다. 상세 선택표는 [alltynex_font.py](../tools/alltynex_font.py)에 있다.

토큰은 자모 인덱스를 비트에 직접 담는 값이 아니라 음절의 조합 정보를 찾는 식별자다. 토큰표에는 코드·음절·Unicode·빈도·출처 행 수·초중종성 인덱스·FNT 슬롯·자모 유무가 들어간다. `composition_payload = (초성<<10)|(중성<<5)|종성`은 검산용이다. 런타임은 CSV를 읽지 않고 빌더가 만든 자모 포인터 표를 사용한다.

- 새 음절은 빌드 때 자동 추가한다. 기존 코드와 token_index는 유지하고 번역에서 삭제한 음절도 표에 남긴다.
- 표의 표시 순서는 가나다순이며 런타임 표는 token_index 순서다.
- 빌더는 토큰표를 읽을 때 형식을 검사한다. 중복 코드·음절, 잘못된 코드 길이·16진수·범위·인덱스를 거부한다.
- 현재 표는 218개, 번역 사용 음절은 215종이다. 사용하지 않는 굳·역·질은 코드 보존 때문에 남아 있다.
- 현재 lead는 F0/F1, trail은 40~7E와 80~FC이며 최대 376개 음절이다. 초과하면 명시적인 오류로 중단한다.
- 자모 조합 자체는 현대 한글 11,172음절을 계산할 수 있다. 이는 현재 토큰 공간에 11,172개를 동시에 적재할 수 있다는 뜻은 아니다.

전수 정적 검사에서 11,172음절이 참조하는 344개 슬롯은 모두 데이터가 있고 0~359 범위 안이다. 360개 중 미참조 빈 슬롯 16개는 오류가 아니다. 현재 전체 CSV 152행 중 한글 포함 59행에서 592회·215종 음절이 사용된다.

### 게임의 EGB 후크

1. 공용 문자열 래퍼 `0x33C94`에서 진입한다. 원본은 문자열 테이블을 스택에 복사하므로 후크는 주소가 아니라 86바이트 레코드 내용으로 대상 행을 찾는다.
2. 최초 대상 출력에서 게임 파일 로더 `0x2AA10`으로 HANME.FNT를 적재하고 정상 상태를 저장한다. 이후 다시 읽지 않는다.
3. 토큰이 가리키는 초성·중성·종성의 72바이트를 OR한다. 받침 없는 음절은 종성을 합성하지 않는다.
4. 비한글 세그먼트는 원래 EGB AH=60 래퍼로 출력하고 한글 비트맵은 AH=23으로 그린다. 원래 EGB 작업 버퍼와 전경색을 사용하며 PSET으로 출력한다.
5. AH=23마다 DS:EDI에 게임 작업 버퍼를 설정한다. DS:ESI는 비트맵 descriptor, ES는 EGB vector selector다. 원본 TownsOS에서도 이 인자를 요구하므로 FreeTOWNSOS 내부 공통 버퍼에 의존하지 않는다.
6. 래퍼 트램펄린을 통해 원래 명령을 실행하고 레지스터·ES·플래그·스택 및 기존 반환 결과를 보존한다. 비대상 행은 원래 경로로 전달한다.

AH=23 descriptor의 소비 필드는 bitmap offset32·selector16·시작 x/y·끝 x/y, 합계 14바이트다. 좌표 양 끝을 포함한다. EGB 문자열 y가 글자 아래쪽 기준이므로 24px 글리프는 y−23~y에 놓인다.

스탭롤 원본 표는 raw `0x3C6B8`, runtime `0x3C4A8`, 80×86바이트다. 처리기 `0x26704`가 전체를 복사하고 `0x267C8`에서 현재 행을 전달한다. CSV의 39행만 수정하며 나머지 41슬롯과 행 순서를 유지한다. 엔딩은 raw `0x3C41C`, runtime `0x3C20C`부터 6×86바이트이며 `0x1CB38`이 516바이트를 복사한다. 세 구간 모두 같은 후크를 사용한다.

### FNT 실패 동작

실제 FNT 누락은 `0x2AA10`의 fopen 실패에서 `0x2B61C → 0x34BF8` 게임 종료 경로로 들어간다. 잘못된 헤더를 반환하는 mock의 대체 출력과 다르다. 기존 로더는 fread 반환값을 버리므로 런타임에 잘린 파일 전체 길이를 보장하는 구현은 아니다. 배포 빌드는 폰트 헤더·길이·내용 및 ISO 내 일치를 검사한다.

## 5. SPR UI 문자열과 슬롯

원본 압축 P3의 literal 매핑으로 CSV raw 주소를 runtime 주소로 변환한다. 대부분의 UI 차이는 0x210이지만 타이틀 `0x3F32E → 0x3F1FC`는 0x132다. 같은 상수로 모든 주소를 바꾸지 않는다.

원본 문자열의 일본 원문 일치와 앞뒤 @ 공백을 검사한다. @는 위치만 이동하고 SPR 슬롯을 소비하지 않는다. 옵션은 32바이트 고정 레코드 안에서 바꾸며, 그 밖의 문자열은 원래 NUL 다음 정렬까지 확인된 0 패딩만 사용한다. 용량 초과는 주소·필요 크기를 표시하고 중단한다. `%d`, `%1d`, `%000006d00` 서식은 보존한다. 마침표는 기존 콜론 글리프 코드로 저장하되 서식 내부는 바꾸지 않는다.

ATTACK THE ENEMY·HIGH SCORE TABLE의 검증된 공백 배치는 해당 주소·출력 문구로 선택하며 삭제한 영문 참조 열에 의존하지 않는다. ASCII_UI와 SPR_TITLE의 같은 타이틀 주소는 한 번만 적용한다. 값이 같거나 하나만 원문에서 바뀌었으면 해당 문구를 적용하고 둘 다 다른 수정값이면 충돌 오류를 낸다.

스코어 하단은 실제 문자 수(@ 제외)를 세어 시작 슬롯을 `min(0x2E7,0x2FD-문자수)`로 정한다. 허용 하한은 0x2E6이며 원본 `0x2D227` 명령의 immediate를 확인해 바꾼다. 현재 하단 23글자 슬롯은 0x2E6~0x2FC, RANKING은 0x2FD~0x303이다. 타이틀 하단 0x348~0x35E와 PRESS RUN 0x334~0x343도 겹치지 않는다. 메뉴는 매 프레임 0x384~0x3FE를 초기화한다.

### LAST AREA의 주황색 N

NOW@LOADING은 시작 슬롯 0x3BA, 좌표·이동폭 6비트 고정소수점으로 출력한다. @를 뺀 NOWLOADING의 10글자가 0x3BA~0x3C3을 사용한다. 두 번째 N의 슬롯은 0x3C2, 글리프 0x9E, 색 테이블 0x8100이다. 원래 인자는 X=0x1300, Y=0x1C00, 이동폭=0x200이며 공백 포함 인덱스 9에서 `(148,112)`가 된다.

원본 FORTH AREA는 9슬롯, LAST AREA는 8슬롯만 덮어쓴다. `0x13C58~0x13C84`의 활성화 루프가 32개 객체의 +0x28·+0x14를 켜므로 남은 0x3C2도 표시된다. LAST DEFENSE LINE은 0x3C3부터 `(52,100)`에 놓여 잔존 N이 오른쪽 96px·아래 12px에 보인다. 문구에 N이 삽입된 현상이 아니다. 영문 패치도 같은 장면 코드·LAST AREA를 사용한다.

현재는 `0x13C88`의 MOV EAX,[0x8EE94] 5바이트를 정리 함수 CALL로 바꾼다. `0xD9350`의 함수는 PUSHFD/PUSHAD로 상태를 보존하고 SPR 래퍼 `0x33D7C`로 슬롯 0x3C2에 빈 패턴 0x80·속성 0xA100을 설정한 뒤 원래 MOV를 실행해 복귀한다. 기존 후크 예약 공간 마지막 0x80바이트를 사용하며 0 내용과 중첩을 검사한다. EXP·ESP를 늘리지 않는다. 실제 화면 테스트에서 잔존 N이 사라진 것이 확인됐다.

다른 짧아진 문구의 남은 슬롯도 검수했다. 로딩 전 `0x28E4C`는 0x3BA~0x3D9를 숨겨 ATTACK THE ENEMY의 잔여 0x3D1~0x3D6이 NOW LOADING과 겹치지 않는다. LAST AREA IS OVER 역시 전체 초기화 뒤 출력한다.

## 6. 메모리 배치와 엔딩 보호 예외

### 확정 원인

추가 엔딩 포인터 목록을 원본 게임 PMB 로더의 스택 파형 버퍼가 덮었다. 사용자 중단 `000C:000D8919`에서 EAX=0x3FC24, EBX=0xE2D0E, EBP=0xF7EBC, ESP=0xF2828이며 두 번째 인자가 `2E 7E 7F 7E`=0x7E7F7E2E로 손상됐다. 파일에는 0xE2C62가 있어야 했다.

| 추적 단계 | 근거 |
| --- | --- |
| 오프닝 0x2D730 | 로컬 스택 0x5604와 저장 레지스터 |
| 0x2EBFC→0x33348→0x395C4 | AL_OVER.EUP의 SATOSHI.PMB 적재, 남은 인자 0x2C |
| PMB 0x395C7 | SUB ESP,0x1012C |
| 0x3978F·0x39796 | LEA EAX,[EBP−0x10000] 파형 버퍼에 fread |
| PMB EBP | F7EBC−5604−C−2C−8−C−8−8=F285C |
| 파형 버퍼 | E285C |
| 마지막 샘플 | PMB 헤더 F952, 파형 F972, 길이 F82 |
| 일치한 손상 바이트 | FE24의 2E 7E 7F 7E, 파형에서 4B2 떨어짐 |
| 실제 덮어쓰기 | E285C+(FE24−F972)=E2D0E |

마지막 파형 적재 범위 `[0xE285C,0xE37DE)`가 당시 엔딩 목록 0xE2D0E~0xE32AA를 포함했다. 오프닝이 먼저 정상 출력되어도 끝의 음원 적재가 뒤쪽 엔딩 데이터를 손상시킬 수 있었다. 이미지 끝이 초기 ESP보다 낮다는 검사만으로 충분하지 않았다.

### 최종 수정과 빌드 경계

사용하지 않는 전체 레코드 사본 74×86=6,364바이트를 제거했다. 정렬을 포함해 6,368바이트 줄여 이미지 끝을 E32C0에서 E19E0으로 내렸다. 실제 세그먼트와 포인터 목록은 유지한다.

| 항목 | 현재 값 |
| --- | --- |
| EGB 후크 | 0xD73D0, 생성 코드 5,747바이트 |
| 후크 예약 | 0x2000바이트 |
| SPR 정리 함수 | 0xD9350 |
| 트램펄린 | 0xD93D0 |
| 실행 이미지 끝 | 0xE19E0 |
| 초기 ESP | 원본 0xF7F00 |
| PMB 경로 스택 예약 | 0x16000 |
| 예약 하한 | 0xE1F00 |
| 이미지 끝과의 간격 | 0x520=1,312바이트 |

확인한 오프닝·PMB 프레임 기본 합계는 약 0x15748이며 0x16000은 하위 CRT 호출 여유를 포함한다. 이 경계를 넘으면 빌드를 중단한다. 초기 ESP를 이동해 피하지 않는다. 초기 ESP=0x10A3C0으로 옮긴 시험에서는 사용자가 새 ISO 재시작 후 보스 이상을 보고했고 CRT 힙 시작도 바뀌므로 철회했다. 보스 이상의 상세 기전까지 확정한 것은 아니다.

원본 코드 영역의 허용 변경은 EGB 진입 `0x33C94`의 6바이트, N 정리 호출 `0x13C88`의 5바이트, 스코어 슬롯 immediate `0x2D228`의 4바이트다. 그 외 기존 코드·작업 버퍼의 예상 밖 변경은 발견되지 않았다.

### Free386 예외 화면 해석

캡처 Err=00003795는 CPU 오류 코드로 해석하지 않는다. 예외 출력기 0xAD0 이후 0xB25에서 EDX를 플래그 문자열 주소 0x3795로 바꾸고 0xB88→0xAB9가 이를 Err에 출력한다. 보고기의 오류이며 게임 포인터 손상 원인은 별개다.

보호 예외(#GP)의 진입 코드 0x15A4가 0x0D를 PUSH해 0x1600으로 진입하며 원래 스택에 DS/EAX를 저장한 뒤 별도 예외 스택으로 옮긴다. ECX·ESI·EBP와 CPU의 CS:EIP는 오류 분석에 사용할 수 있다. 예외 주소 0x14337, ECX=0x7E7F1E2E·ESI=0x7E7F1E34는 잘못된 레코드 길이 판독과 일치한다. 표시 SS:ESP는 동일 CPL에서 예외 직전보다 28바이트 낮아 후크 호출 직전 ESP와 같다고 가정하지 않는다.
