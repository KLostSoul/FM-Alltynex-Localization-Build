# Alltynex 문자열 CSV 안내

## 파일 구성

| 파일 | 용도 |
| --- | --- |
| [Alltynex_Korean.csv](Alltynex_Korean.csv) | 원문·패치 문자열·EGB 출력 좌표를 편집하는 번역표 |
| [Alltynex_Hangul_Tokens.csv](Alltynex_Hangul_Tokens.csv) | 번역에 사용한 한글 음절의 토큰과 자모 조합 정보를 저장하는 자동 갱신 표 |

번역은 `Alltynex_Korean.csv`에서 편집한다. 토큰표 생성 명령을 실행하거나 빌드하면 새 한글 음절을 찾아 `Alltynex_Hangul_Tokens.csv`에 추가한다. 게임은 CSV를 직접 읽지 않으며, 빌더가 CSV를 문자열 레코드와 런타임 조합 표로 변환해 ISO에 넣는다.

## 번역 CSV 열

| 열 | 의미·편집 방법 |
| --- | --- |
| `type` | 출력 종류. EGB_STRING은 본문, ASCII_UI·SPR_TITLE은 기존 SPR 문자 경로다. 원래 값을 유지한다. |
| `exp_offset` | 패치 대상의 원본 EXP 주소. 원래 값을 유지한다. |
| `x`, `y` | EGB의 시작 X좌표와 글자 하단 Y좌표(px). X는 편집할 수 있으며 Y는 원본 값을 유지한다. SPR 행은 비워 둔다. |
| `japanese_original` | 원본 문자열 참조. 원문의 전각 공백도 보존한다. |
| `korean_patch` | 빌드에 적용할 문자열. 한글 본문과 기존 영문·숫자 SPR 문구를 이 열에서 편집한다. |
| `notes` | 번역·작업 메모. 화면 출력에는 사용하지 않는다. |

### 편집 규칙

- CSV는 UTF-8로 저장하고 헤더·행 순서·주소·출력 종류를 유지한다. 쉼표가 들어간 문자열은 CSV 인용 규칙에 따라 저장한다.
- 현재 빌드는 오프닝 29행·스탭롤 39행·엔딩 6행의 EGB와 SPR UI 77개 주소를 적용한다.
- EGB 본문은 인코딩 후 최대 79바이트다. 한글 음절은 2바이트 토큰을 사용하며, 비한글은 CP932로 저장한다. 화면 너비를 넘는 문장은 기존 행 사이에서 번역을 재배치한다. 행 수와 주소는 유지한다.
- EGB의 `x` 값은 시작 좌표로 직접 적용한다. 오프닝 29행은 CSV의 행별 X좌표를 사용하며 현재 값은 80px 21행, 32px 5행, 56px 2행, 0px 1행이다. 스탭롤·엔딩 45행은 X=80px에서 시작하고 앞쪽 전각 공백으로 배치한다. 공백은 12px, 다른 문자는 24px 이동한다. 정렬에 쓰는 공백을 임의로 삭제하지 않는다.
- SPR UI는 출력 가능한 ASCII 문자만 사용할 수 있다. `%d` 같은 출력 형식 지정자는 유지한다. 빌더는 각 문자열의 저장 바이트 용량을 검사하며, 스코어 하단은 표시 슬롯 23개 한도도 검사한다.
- 본문에는 NUL·줄바꿈·탭·ESC와 `U+0080`을 포함한 C0·C1 제어문자를 넣을 수 없다. 한글 토큰과 충돌하는 CP932 사용자 정의 문자도 사용할 수 없다. SPR UI는 출력 가능한 ASCII 문자만 허용한다. 빌더가 검사한다.
- 스탭롤의 빈 번역은 문구를 지우되 레코드와 스크롤 간격은 유지한다.

## 조합 토큰 CSV

`Alltynex_Hangul_Tokens.csv`는 번역표에서 생성·갱신한다. 기존 `token`과 `token_index`는 유지하고 새 음절만 추가한다. 행은 음절의 가나다순으로 정리하지만 런타임 표는 `token_index` 순서로 만든다. 번역에서 빠진 음절도 기존 코드 보존을 위해 남긴다. 일반 번역 작업에서는 토큰이나 자모 슬롯을 직접 수정할 필요가 없다.

## 대상과 범위

`Import/Strings/Alltynex_Korean.csv`의 korean_patch 열에서 완성형 음절을 조사한다. 현재 전체152행 중 한글을 포함한59행에서592회,215종 음절이 사용된다. 이전 표의 코드도 유지하므로 토큰표는218행이다. 현재 번역에서 사용하지 않는 굳·역·질도 기존 코드 보존을 위해 남아 있다.

## 표의 조합 구조

각 토큰은 한글 음절 하나를 가리키며, `initial_index`, `medial_index`, `final_index`가 초성·중성·종성의 조합을 나타낸다. 종성 인덱스 0은 받침이 없다는 뜻이다. `composition_payload`는 `(초성 인덱스 << 10) | (중성 인덱스 << 5) | 종성 인덱스`로 계산한 검산용 값이다.

`hanme_initial_slot`, `hanme_medial_slot`, `hanme_final_slot`은 ISO 안의 24×24 `HANME.FNT`에서 실제로 읽어 OR 합성할 부품 셀 번호다. 이 FNT는 완성 음절 비트맵 모음이 아니라 문맥별 자모 조각 360개를 담는다. 빌더는 각 음절의 슬롯을 FNT 셀 주소 세 개로 바꾸어 런타임 표에 기록한다. 실행 후크는 이 주소를 사용해 자모를 합성하며, 토큰 바이트에서 초·중·종성 인덱스를 읽지는 않는다. 받침 없는 음절의 종성 주소는 0이다.

토큰 바이트는 Shift-JIS 사용자 정의 영역의 2바이트 값으로 배정했다. 새 음절은 사용 가능한 토큰을 순서대로 받는다. 이 토큰 값은 조합 인덱스를 바이트 안에 직접 인코딩하는 값이 아니라, 표에서 음절 조합 정보를 찾기 위한 식별자다.

## 표 열

| 열 | 의미 |
|---|---|
| `token`, `token_hi`, `token_lo` | 2바이트 토큰의 연속 표기와 상·하위 바이트 |
| `token_index` | 기존 코드를 유지하는 런타임 표 인덱스 |
| `syllable`, `unicode` | 완성형 음절과 Unicode 코드 포인트 |
| `frequency`, `source_rows` | 현재 한글 CSV에서의 출현 횟수와 포함된 문자열 행 수 |
| `initial`, `medial`, `final` | 분해된 초성·중성·종성 자모 |
| `initial_index`, `medial_index`, `final_index` | 조합에 쓰는 자모 인덱스 |
| `composition_payload` | 초·중·종성 인덱스를 합친 검산용 비트 필드 |
| `hanme_*_slot` | 24×24 FNT에서 읽을 실제 부품 셀 번호 |
| `font_components_nonempty` | 참조 셀에 실제 픽셀이 들어 있는지 검사한 결과 |
| `source` | 번역 CSV 출현 여부와 이전 표 보존 여부 |

## 런타임 사용과 기존 검증 기록

표의 모든 FNT 셀 번호가 0~359 범위 안에 있고, 참조 셀은 모두 비어 있지 않은 것을 확인했다. ISO에 포함하는 `HANME.FNT`의 기록된 MD5는 `324968380BF92353565FDAFF3AB38920`이었다.

빌드할 때 218개 행의 자모 슬롯을 token_index 순서의 자모 주소 표로 만든다. 또한 EGB 후크가 처리할 문자열을 빌드 시 해석해, 각 한글 토큰에 해당하는 자모 주소 표 항목과 비트맵 출력 위치를 문자열별 메타데이터에 기록한다. 실행 후크는 이 메타데이터의 주소를 따라 자모를 합성하고 출력한다. 런타임에서 CSV를 읽거나 문자열의 토큰을 다시 분석하지 않는다. 오프닝 29행·스탭롤 39행·엔딩 6행에 적용된다.

토큰표 생성 명령과 빌드에서 새 음절을 추가하고 기존 토큰을 유지한다. 표의 표시 순서는 가나다순, 런타임 인덱스 순서는 token_index다. 현재 F0/F1 토큰 공간은376개 음절이다. 11172개 완성형 음절의 자모 조합 자체는 가능하지만 한 번의 이 토큰표에11172개를 모두 넣을 수 있다는 뜻은 아니다.

재생성 스크립트: `tools/build_hangul_composition_token_table.py`

폰트 형식과 실제 출력 과정은 [한글 빌드 안내](../../doc/Alltynex-Korean-Build.md#4-fnt조합-토큰음절-합성)에 있다.
